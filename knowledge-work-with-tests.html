Knowledge Work, With Tests: A Year of Building a Public Research Wiki With LLM Agents

Published on May 13, 2026

For the past year I have been quietly building a public knowledge product about Nepal's electricity system — a wiki paired with an interactive map, a structured project database, and a working static site at transparentgov.ai/wiki/explorer. Hydropower, transmission, storage, solar, trade — the kind of thing that would normally live as a 90-page PDF and be read by twelve people in a ministry.

What makes the project interesting to me, and what this post is about, is not the content but who wrote it. Almost every page on the wiki was drafted by an LLM agent, cross-linked by one, restructured by one, and stitched into the master argument by one. Source pages were summarized from primary PDFs. Project records were filled in from annual reports. Claims got their boundary conditions written by one agent and pressure-tested by the next. Map layers got their popup language drafted, then reframed, then audited for hierarchy creep. I curated, reviewed, made the structural calls, and set the bounds. The agents did the writing.

This is not a story about letting AI tinker with prose I had already written. It is a story about what it took to let AI build a serious public knowledge product end-to-end — across many editing sessions, with new pages being drafted and old ones being refined in the same week — without the whole thing slowly degrading into plausible average. The interesting result is not that LLM agents can build it. They can; that is now uncontroversial. The interesting result is what I had to do to the repository before they could build it well, and what the audit log caught when they slipped.

The pattern that emerged, after a year and a great deal of audit-log reading, is that knowledge work scales the same way a codebase does — with versioned rules, validators, tests, and a build that fails when the rules are broken. The five files in the next section are that scaffolding. Without them, every session left the corpus a little worse. With them, every session left it measurably better, and the audit log can prove it.

Five files standing between agents and a knowledge corpus.

The Problem I Was Actually Afraid Of

If you have spent any time letting an LLM agent edit a codebase, you know the failure modes. Type errors. Runtime exceptions. Broken tests. Imports that point at the wrong file. They are loud. They show up in CI. The whole industry has tools for catching them.

Letting an LLM edit a knowledge corpus is not the same kind of problem. The bad outcomes there are quiet. A source page picks up a sentence of interpretation. A data page picks up a recommendation. The canonical definition of "seasonal mismatch" drifts into "winter crisis" on one page and "monsoon-export-dry-import asymmetry" on another. A source page's Used By list expands to include pages that should cite the source but don't actually cite it. Two contradictory numbers from two different reports get smoothed into one consensus paragraph that does not match either source.

None of that breaks a build. None of that looks wrong in a diff. Each individual edit is plausible. The damage shows up after twenty sessions, when a reader notices that the wiki's central definition has changed three times and nobody can remember which version is right.

That was the thing I was actually afraid of. Not the agents being bad at editing — they are perfectly competent at editing. I was afraid of them being competent at editing toward an average prose, when the whole point of a research wiki is that specific claims, with specific sources, in specific places are what give it value.

Why the Prompt Wasn't Enough

The first thing I learned is that you cannot solve this in the prompt. I tried. Long system prompts, careful task descriptions, "be source-disciplined" instructions. They worked for the first half of a session and then dissolved as context filled up with other concerns. Asking an LLM to remember a discipline across a session is asking it to do something it is structurally not good at.

What did work was moving the discipline into the repository itself. Not as documentation that an agent might read once, but as a set of files an agent has to pass through to do anything useful. Governance documents that define the hierarchy. An ontology file that locks the canonical terms. Templates per page type. Validators that run before commits. An audit log that every session writes to.

I started thinking of this as code-adjacent infrastructure. It is not code in the runtime sense — none of it executes when the site is built. But it is code in the every-future-edit-has-to-respect-this sense. The repository becomes the second editor. The prompt only tells the agent what to do; the repository tells it what it must not do, and makes the difference visible.

The set converged on five files, and they are small enough to fit in a single screenshot:

wiki/GOVERNANCE.md          # authority hierarchy + invariants
wiki/ONTOLOGY.md            # canonical terms, allowed and disallowed aliases
wiki/TEMPLATES.md           # canonical section structure per page type
wiki/QUALITY_RUBRIC.md      # tier definitions and target distribution
wiki/FLAGGED_FOR_REVIEW.md  # running unresolved-issues log
wiki/WIKI_AUDIT_LOG.md      # session-by-session record
docs/session-template.md    # the prompt wrapper editors paste in
scripts/validate_repo.py    # hard-fail and warn-only structural checks
scripts/check_source_used_by.py

Under two thousand lines of markdown and a few hundred lines of Python. The rest of this post is about what each file does, and — more interesting to me — what they actually caught when I went back and read fifty sessions of audit log entries.

The Five Files

1. The authority hierarchy

The single most important file in the repository is wiki/GOVERNANCE.md. The first thing it does is sort every page in the wiki into one of four authority levels.

Sources sit at the bottom. They describe primary materials — annual reports, PDFs, registries — and they are explicitly forbidden from interpretation. Above them, data pages, entity pages, and claim pages present structured facts and evidence-backed arguments, but they must not contain strategic implications. Synthesis pages sit above those — the only layer where "so what" belongs. And at the top, a single master thesis page acts as the cross-synthesis frame for the whole wiki.

The hard rule is that interpretation can move upward only. A claim page can cite a data page; a data page must not contain claim-page reasoning. A synthesis page can cite a claim; a claim must not pre-emptively conclude the synthesis. If you find an argument leaking downward, it must be moved up to its proper layer, and the lower page should link to it.

This sounds almost philosophical, but it is the most operationally useful rule in the whole system. Once it is enforceable, a remarkable amount of fuzzy editorial argument simplifies. "Should this paragraph live on the source page or the claim page?" becomes a single question: is it interpretation? If yes, it must move up.

Beneath the hierarchy, the same file lists ten non-negotiable invariants. Most of them are prohibitions. No quantitative claim without source linkage. No confidence inheritance across claims. Never replace sourced text with paraphrased summaries. Never remove interpretive content without verifying downstream existence first. I wrote them as prohibitions on purpose. A list of things to do expands forever; a list of things that must not happen is finite, and a validator can check most of it.

2. The ontology

The second file, wiki/ONTOLOGY.md, locks the canonical terms. For every load-bearing concept in the wiki — seasonal mismatch, storage deficit, firm power, run-of-river hydropower, stranded generation, solar-hydro complementarity, sediment as design constraint — it gives a definition, a list of allowed aliases, a list of disallowed aliases with reasons, and pointers to parent synthesis pages.

The disallowed aliases are the part that does the work. "Winter crisis" is forbidden, not because it is wrong, but because it is too narrow — it implies dry-season shortage only, when "seasonal mismatch" is the broader monsoon-surplus-plus-dry-deficit pattern. "Solar replacement" is forbidden because it mischaracterizes the argument — solar does not replace hydro, it complements it. Recording the disallowed term, with the reason, is what prevents an agent from drifting into it on the next session and a human reviewer from waving it through.

The other thing the file does is make new term introduction a procedural step. New terms get flagged in a separate review file before they are used. They do not enter the ontology by accumulation; they enter by review. This single rule has done the most to prevent terminology fragmentation across editing sessions. Before it existed, three sessions could leave the wiki with three different canonical phrases for the same concept and nobody had decided which was preferred.

3. Templates per page type

Each of the seven page categories — sources, entities, concepts, claims, data, syntheses, interventions — has a canonical section structure, tied to an exemplar page. Source pages get ## Summary / ## Key Findings / ## Relevance / ## Limitations / ## Used By. Claim pages get ## Claim / ## Evidence / ## Confidence Rationale / ## Unresolved Issues / ## Boundary Conditions / ## Related. And so on.

This sounds bureaucratic. In practice it is what makes pages comparable. A reader who has read one claim page can read any claim page; the order of sections is the same, the kind of content in each section is the same, what the page is for is the same. Boring is good. Boring is what lets a reader navigate three hundred and eighty pages without learning a new convention on each one.

4. Validators

Templates are useless without enforcement, so scripts/validate_repo.py runs as part of make validate on every commit. It has two tiers of checks.

The hard-fail checks block the build. They catch broken wikilinks (case-sensitive — many of these would survive human review), cache mismatches between page files and the explorer's JSON indexes, layer-manifest references to GeoJSON files that don't exist, project slugs in the structured CSV that don't have wiki pages, duplicate claim_ids, public-language slips like the names of specific AI providers showing up in the README, and tracked files that should never be in version control. About a thousand lines of Python; most of it is small.

The warn-only checks are the more interesting half. They surface pages missing canonical section headings per category, entity pages of certain generator types missing their ## Sources section, status fields in frontmatter that disagree with the structured CSV. Crucially, they are tier-aware. An auto-stub entity is correctly minimal — it does not get warned about for missing ## Limitations. A brief-tier page needs a Summary but not a full controversies section. The tiers live in the quality rubric file; the validator just reads them.

The first version of the validator printed every individual warning. Six hundred and ninety-six of them. Nobody read the output. I rewrote it to emit a category-by-category summary instead, with the full list one environment variable away. The change took twenty minutes and is the reason the validator actually gets read every commit:

WARN: missing required sections (warning only — not a hard fail)
        — skipped 72 record-tier pages
  claims:   0 pages missing ## Boundary Conditions
  concepts: 31 pages missing ## Summary
  concepts: 31 pages missing ## Simple Explanation
  concepts: 31 pages missing ## Common Misunderstandings
  data:     23 pages missing ## Summary
  ...

The summary tells an editor the next move. The full list, with WIKI_VERBOSE=1, is for when you want it.

A second, smaller validator — scripts/check_source_used_by.py — is more specific. For every source page, it builds the actual set of exact backlinks from the rest of the wiki, compares it to the page's declared ## Used By list, and prints the diff. It is one of the most consequential thirty lines of Python in the project, and I'll come back to why in a moment.

5. Bounded sessions and the audit log

The fifth file is procedural. Every editing session is bounded — five pages at most, no exceptions — and every session is logged.

The session template is a prompt wrapper. An editor (human or agent) pastes it as the first message of any session. It declares the category, lists the five pages, names the exemplar, points at the governance and ontology files, and asks the agent to read all three before starting. It defines a four-step per-page loop — diagnose, propose, flag, confirm — and lists stopping conditions: split-or-merge decisions, contradictions across pages, uncertainty about which category a piece of content belongs to.

After the session, the editor writes an entry in WIKI_AUDIT_LOG.md. It is now the most-read file in the repository after the master thesis. Every entry follows the same shape — pages touched, validation delta, flags raised, patterns observed, decisions made. Something like this:

2026-05-11 — Concepts Pass (Second Cycle, Session 5)

Pages touched: concepts/stranded-generation, concepts/seasonal-mismatch, concepts/seasonal-arbitrage-trap, concepts/q-design-discharge, concepts/ganges-contribution — added ## Summary, ## Simple Explanation, ## Common Misunderstandings on all five.

Validation: 548 → 533 warnings (−15). Flags raised: none. Pattern observed: third policy prescription found on a concept page across full audit — consistent with the structural prediction that concept and data pages absorb analysis that hasn't found its synthesis home.

The first three fields — pages touched, validation delta, flags raised — are accounting. The last two — patterns observed, decisions made — are where the real research artifact lives. Over fifty sessions, the "pattern observed" line accumulates into something with empirical weight. That is what the next section is about.

What the System Actually Caught

The point of writing the audit log is that patterns across sessions become visible. After eight weeks of edits and the better part of two hundred pages reviewed, four findings stood out.

Where interpretation bleeds downward

The single most useful empirical finding the audit log produced was that hierarchy violations have an obvious category signature. They are not evenly distributed; they cluster.

Sources and data pages were the riskiest categories by a wide margin. Sixty percent of sampled source pages contained interpretive language that belonged on a claim or synthesis page. Forty percent of data pages contained outright recommendations. Concepts had one violation in five pages. Claims and entities had zero across the same sample.

The reading is structural, not personal. Source pages and data pages are the closest to the evidence — they are the natural place to write down what you noticed when you read the source, or what the table seems to imply. Both intuitions are wrong, and both produce the worst kind of drift: interpretation hidden inside evidence. The same finding showed up on three different occasions, in three different categories — data-storage-comparison, concepts/buildability, data-solar-hydro-complementarity-profile — each time with a different agent on a different day. After the third one I added a tenth invariant to the governance file: no policy prescriptions on concept or data pages. The pressure to write them was structural, so the rule had to be too.

What surprised me about this is how clean the signal was. Within five weeks, an audit log written down longhand was producing a statistically useful map of which page categories were absorbing the wrong kind of content. That is not a result you can extract from an individual session; you can only see it after a hundred sessions of audit-log entries say similar things.

The template-adoption gap

The other big pattern was less dramatic and more useful. Across five categories — claims, concepts, sources, data, entities — the same kinds of section were missing, cohort-wide. Four of five claim pages lacked their ## Boundary Conditions section. Five of five concept pages lacked ## Simple Explanation and ## Common Misunderstandings. Source pages were missing ## Limitations and ## Used By at similar rates.

This was not the agents' fault. The templates were written after most of the pages. The pages weren't drifting; they pre-dated the rule. Once the validator started counting, the gap became a measurable program of work rather than an indefinite editorial burden:

The warning count fell from 696 to 593 once the tier-aware filter went in — record-tier auto-stubs are correctly minimal and should not be counted against the gap. Then it fell session by session as the cohorts were retrofitted. Claims hit zero structural warnings first, on the second session of the second cycle, when all sixteen claim pages had a canonical ## Boundary Conditions section. That chart, more than anything else, is what convinces me that bounded sessions with a validating counter are the right shape for this kind of work.

Citing by memory

The clearest single-mechanism failure the system ever caught was on a source page's ## Used By list. Early in the project, an agent rebuilding the Used By section reconstructed the list from recall — what pages it thought cited the source. The list looked plausible. It included pages that did not cite the source, and excluded pages that did.

The fix was a one-line rule in the session template and a thirty-line Python script. The rule: the ## Used By section must be built from a grep against the wiki, never from memory. The script does the grep automatically and prints the diff. It now runs as part of make test.

What is interesting about this is that the agent was not really the problem. Humans had been doing the same thing — reconstructing citations from memory — for years on similar artifacts. The validator made the failure mode visible, and the rule turned the discipline into a procedural step. After the rule went in, ten consecutive source-page edits passed the validator on first attempt.

The audit log is a claim, not a fact

A subtler failure showed up weeks later, during an external review pass: two edits recorded in the audit log had not actually been written to disk. The log said +## Boundary Conditions had been added to claim-mw-not-equal-value. The file did not contain it. Root cause unknown — maybe an edit-tool failure, maybe a revert, maybe a proposal that was confirmed but never executed.

The fix was procedural: the audit log must be verified against file contents before pushing. The deeper lesson is that the audit log is a claim, not a fact. It is as susceptible to drift as any other document in the corpus, and needs its own validation step. Currently that runs as a periodic spot-check; eventually it should be automated.

What Didn't Work

This part is more useful than the previous part, and I want to be careful not to oversell what I built. Several things did not work, or worked at a cost I should be honest about.

Five-page sessions are slow. The five-page-per-session bound is the most-felt cost in the system. It limits an editor to maybe twenty pages a week of paid attention. For a wiki of 380 pages and another four hundred candidate slugs, that is a long horizon. I tried relaxing it twice. The first relaxation — a six-page batch with parallel writes — worked, but only because every page had the same diagnosis (missing ## Boundary Conditions) and zero flags. The second relaxation, on a heterogeneous batch, produced an unresolved category mistake and was reverted to the five-page bound. The rule I now follow is that bounded scope is hard for heterogeneous batches and soft for uniform batches.

The validator is hygiene, not research. Validators catch structural drift. They do not catch analytical mistakes. A page can have a perfect Summary, Simple Explanation, and Common Misunderstandings section, in the right order, and still contain the wrong number. The validator is silent. This is correct behavior — calibrating confidence is what humans are for — but it is also a real limit. A reader who sees OK: 378 wiki pages should conclude that 378 pages are structurally compliant, not that 378 pages are correct. The two are different.

Confidence drift is unsolved. The wiki tags claims with confidence flags — high, medium-high, medium, low. The ontology declares a canonical confidence per claim. Page frontmatter declares one per claim. In principle these should agree. In practice we found one disagreement per major audit pass. Resolution requires a human reading the underlying evidence and choosing.

Ontology drift is constant. Every editing session produces at least one terminology question. The protocol — flag in the review file, defer to monthly review — works. It also produces a steady backlog. There is no version of this system in which the ontology is "done." There is a version in which it is well-maintained, and that is sufficient.

Categories are part of the API. I rewrote the page-type taxonomy once — splitting concepts and claims into separate categories — and the validators, ontology, templates, audit log, and session template all needed to be updated together. There is no atomic operation for "rename a category." Each rename produced a small cascade. The lesson is to treat the categories themselves as load-bearing API and version them deliberately.

The General Pattern

The five mechanisms are not specific to wikis, energy, or Nepal. They are specific to long-lived corpora edited in sessions by mixed teams. That includes country dossiers, sector primers, multi-author academic projects, internal corporate knowledge bases that accumulate across teams and years, regulatory or compliance corpora, even code documentation systems where the docs have their own evidentiary structure.

The shape stays the same. What changes is the content of the rule files. The authority hierarchy might be source → finding → claim → recommendation, or evidence → analysis → memo, or interview → coding → theme → theory. The ontology might be terms of art in a different domain. The templates change with the kinds of artifact involved. What does not change is the principle that the rules live in the repository, the validators enforce structural invariants, and every session leaves an audit-log entry.

One cross-cutting prediction is worth flagging. For any sufficiently large corpus, interpretation will accumulate on the lowest-authority pages. The data page or source page absorbs the analyst's notes because it is the closest to the evidence and the easiest place to write them down. The pressure is structural, not personal. The mechanism that resists it — the hierarchy rule, the downstream-check, invariant nine — has to be enforced for the duration of the corpus's life, not the duration of one editorial pass.

Repository as the Second Author

The phrase I keep coming back to is repository as the second author. The prompt sets the task. The model produces the words. The repository — through governance, ontology, templates, validators, and audit log — sets the constraints that decide whether those words become part of the corpus or get sent back. None of those constraints are exotic. None of them require model-specific knowledge. They are all things you would already want for a serious editorial project, just written down where an editor of any kind — human, agent, future me — has to read them.

I think this is the part that generalizes beyond LLM editing. Knowledge corpora have always had this problem; LLMs just made it visible. Once you have an editor — any editor — operating in bounded sessions across many years, you need the rules to live somewhere both legible and enforceable. The repository turns out to be the right place. The agents just made the cost of not doing this expensive enough that I finally wrote it down.

The wiki is at transparentgov.ai/wiki/explorer. The kit — GOVERNANCE.md, ONTOLOGY.md, TEMPLATES.md, validate_repo.py, the audit log, the session template — is small enough to lift in an afternoon. If you copy it into a different corpus and the same patterns repeat, or fail to repeat, I would like to hear about it. The interesting question is whether the result generalizes; the only way to find out is to run the experiment in a second place.
